# 12단계 검증 절차: 자동 시험과 수동 시험

이 문서는 `npm run ops:verify`가 만드는 검증표(`artifacts/ops-verify.json`, Git에 올리지 않음)의 **수동 항목**을 사람이 그대로 따라 할 수 있게 적은 것입니다. 표의 `상태` 열은 세 가지만 씁니다.

| 상태 | 뜻 |
|---|---|
| 실행 | 실제로 요청을 보내 응답을 받았음. `일치`는 기대 결과와 같은지 |
| 미실행 | 필요한 계정·키·기기가 없어 보내지 못했음(사유가 적힘). 통과로 세지 않음 |
| 수동 대기 | 승인된 기기의 패스키 확인이 필요해 사람이 브라우저에서 해야 함 |

`구분`이 `local_function`·`local_file`인 줄은 함수·파일 점검이며 **실제 API 결과가 아닙니다**.

## 준비 (한 번)

1. Supabase SQL Editor에서 `docs/sql/t12_ops.sql`을 실행합니다. (이 표가 없으면 보호 API가 503으로 닫힙니다.)
2. `.env`(Git에 올리지 않음)에 서버 전용 값 `SUPABASE_URL`, `SUPABASE_SECRET_KEY`와 시험 계정 `USER01_*`, `USER02_*`가 있어야 합니다. 값은 이 문서·화면·로그에 쓰지 않습니다. `.env.example`에 이름만 있습니다.
3. 시험 계정의 기기는 11단계 절차(로그인 → 「이 기기 승인 요청」 → SQL `[승인]`)로 미리 승인해 둡니다. 패스키의 개인키는 기기 안에만 있어 이 저장소의 스크립트가 만들거나 대신 서명할 수 없습니다.

## 자동 시험 실행

```
npm run ops:verify
```

- `.env`에 위 값이 있으면 이 저장소의 `api/*.mjs`를 로컬 서버(127.0.0.1)로 띄워 **실제 Supabase에** 요청을 보냅니다. 배포된 서버를 대상으로 하려면 `OPS_BASE_URL=https://... npm run ops:verify`.
- 표의 `요청 ID`는 서버가 응답 헤더 `X-Request-Id`로 준 값이며, 스크립트의 시험 ID(`F1-1` 등)와 다릅니다. 서버 로그와 `t12_access_events.request_id`에서 같은 값으로 찾을 수 있습니다.
- 비로그인·기기 확인 결과 없음·위조 기기 확인 결과 같은 **거부 시험**과 정상 로그인·기기 질문 조회 같은 **정상 시험**만 자동으로 보냅니다. 승인된 기기가 필요한 항목은 표에 `수동 대기`로 남습니다.

## 수동 시험 (브라우저, 승인된 기기)

각 시험 뒤에 **응답 상태, 화면의 「작전실」 요청 ID, 시각**을 표 `artifacts/ops-verify.json`의 같은 `testId` 줄에 직접 적거나, 아래 형식으로 메모해 `docs/OPS_VERIFY_RESULT.md`에 붙입니다. 토큰·비밀번호·메모 본문은 적지 않습니다.

### 흐름 1 — 무인증 조회 → 타인 메모 조회

| 순서 | 조작 | 기대 |
|---|---|---|
| 1 | 로그인하지 않은 상태로 주소창에 `/api/my-notes` 열기 | `401 unauthorized` (자동 시험 F1-1) |
| 2 | USER02로 로그인 → 「이 기기 승인 요청」(이미 승인됐으면 「승인 상태 다시 확인」) → 자료실이 열림 | 화면에 "서버가 이 기기를 등록 기기로 확인" |
| 3 | 개발자 도구 Network 탭에서 USER01의 메모 ID 하나(SQL로 앞 8자리만 확인)를 `GET /api/my-notes/<ID>`로 요청 | `404`, 응답에 메모 내용 없음 (F1-8) |
| 4 | 같은 화면에서 USER02 본인 메모 목록 | `200` (정상 대조) |

### 흐름 2 — 미등록 기기 → 회수된 신원

| 순서 | 조작 | 기대 |
|---|---|---|
| 1 | 승인하지 않은 다른 브라우저/시크릿 창에서 USER01 로그인 | 화면: 승인 대기·자료 없음. 직접 요청도 `403 device_not_registered` (F2-1) |
| 2 | 승인된 기기에서 USER01 정상 요청 | `200` (정상 대조) |
| 3 | SQL Editor: `docs/sql/t12_ops.sql`의 **[회수]**로 USER01 한 명만 회수 | — |
| 4 | **같은 브라우저 세션(로그인·기기 확인 결과 그대로)** 에서 「작전실 새로고침」과 자료 조회 | `403 identity_revoked` (F2-5). 기기 상태는 `approved`로 남아 있어도 닫혀야 함 |
| 5 | USER02(회수 대상 아님)로 같은 시각 정상 요청 | `200` (F2-6) |
| 6 | SQL **[복권]** 실행 뒤 USER01 재요청 | `200` (F2-7) |

기기 회수(`t11_devices.status = 'revoked'`)와 신원 회수(`t12_revoked_identities`)는 별개입니다. 기기만 회수하면 다른 승인 기기는 열리고, 신원을 회수하면 승인된 기기가 있어도 모두 닫힙니다.

### 흐름 3 — 복구 → 서명 없는 변경 요청 → 구역 밖 조회

| 순서 | 조작 | 기대 |
|---|---|---|
| 1 | USER01 시험용 메모를 만들고 `docs/sql`의 10단계 절차로 사본을 만든 뒤, 화면에서 메모를 수정 | `200` |
| 2 | 복원 미리보기 → 복원 실행 | 미리보기 `200`, 실행 `200`, 작전실 「복구 버전·결과」에 `restored` 한 줄 (F3-8, F3-11) |
| 3 | 기기 확인 결과·로그인 없이 `PUT /api/my-notes/<ID>` | `401` (자동 F3-3) |
| 4 | 로그인만 하고 기기 확인 결과 없이 같은 요청 | `403 device_not_registered` (자동 F3-6) |
| 5 | 승인된 기기에서 USER02의 메모 ID로 `GET /api/my-notes/<ID>` | `404` (F3-10) |
| 6 | 승인된 기기에서 USER02의 메모 ID로 `POST /api/note-restore/<ID>` | 거부(사본·소유자 불일치로 중단), USER02 메모 변화 없음 (F3-9) |

> 이 앱에는 요청마다 경로·본문을 서명하는 장치가 없습니다. 여기서 "서명 없는 변경 요청"은 **로그인 토큰과 서버가 승인 기기에만 발급한 기기 확인 결과(`X-Device-Session`) 없이 보낸 변경 요청**을 뜻합니다. 서명 뒤 경로·본문을 바꾸는 시험은 이 앱의 구조에 해당하는 서명이 없어 적용되지 않으며, 실행하지 않았습니다.

### 작전실 화면과 서버 기록 대조 (제작 1 확인)

1. 작전실 화면의 `요청 ID`를 적습니다.
2. SQL: `select outcome, status, request_id from public.t12_access_events where request_id = '<요청 ID>';` 로 같은 값이 있는지, 결과(`allowed`/`device_not_registered`/`identity_revoked`)가 화면 응답과 같은지 확인합니다.
3. 화면의 「기기 회수 상태」 숫자가 `select status, count(*) from public.t11_devices where owner_id = '<본인 UUID>' group by status;`와 같은지 확인합니다.
4. 화면의 「복구」 건수가 `t10_note_backups`·`t10_restore_audit`의 본인 행 수와 같은지 확인합니다. 메모 제목·본문은 화면에도 이 쿼리에도 쓰지 않습니다.

## 41종 시험

저장소·`docs/`·제공 자료에서 41종 시험 **목록과 실행 도구를 찾지 못했습니다.** 이 절차의 항목 수는 41이 아니며, 목록을 임의로 만들거나 통과로 세지 않습니다. 공식 목록이 제공되면 같은 표 형식에 `실행`/`미실행`으로 추가합니다.
