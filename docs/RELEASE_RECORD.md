이 문서는 **학생 진술**입니다. 서버가 새 환경에서 실행했다는 뜻이 아니며, AI 원문 검토는 실행 성공 증명이 아닙니다. 비밀값·로컬 절대경로는 적지 않습니다.

## 4. 버전과 지원 범위

- **상태: 검증 중인 버전입니다.** v1.0이 아니며 실제 운영 인증이 아닙니다. 22단계 통과는 원문 검토 기준의 수료이며 실제 동작 증명이 아닙니다.
- **Node.js 기준을 하나로 정리합니다.**

| 구분 | 버전 | 근거 |
|---|---|---|
| 수업 기준·권장 | 24.19.0 | `on-client/package.json`의 `engines.node`. 실행 도구는 24.19.0이 아니면 "참고" 문구만 출력 |

| 검증하지 않은 버전 | 24.19.0 및 그 밖의 모든 버전 | **미확인** |

- 24.19.0은 **필수가 아니라 권장 기준**입니다. `engines.node`는 정확한 값으로 적혀 있지만 npm은 기본 설정에서 이를 강제하지 않습니다. 실행 도구는 22~24를 허용하며, 그중 22.20.0에서만 서버 시작을 실제로 확인했습니다. 따라서 "22.20.0에서 시작 확인, 22~24는 실행 도구가 허용하는 범위, 24.19.0은 수업 기준이며 미검증"으로 읽어야 합니다.
- Windows 11 외 OS, 브라우저는 확인하지 않았습니다.
- 기본 실행은 실제 접근 제어·XDR 시스템에 연결되지 않은 상태(`disconnected`)입니다. `npm run demo`는 예제 자료이며 실제 연결이 아닙니다.

## 7. 데이터 보존 계획

이 장은 **절차 설명**입니다. 이번 단계에서 아래 백업·복원 명령을 실행하지 않았고 결과도 확인하지 않았습니다. 데이터는 모두 수업용 가상 자료이며 실제 개인정보는 넣지 않습니다.

### 7-1. 보존 대상과 범위

| 구분 | 대상 | 위치 | 범위 |
|---|---|---|---|
| 코드·문서 | 학생 코드, 문서, SQL 스키마 | Git `assignment` 브랜치 | 포함 |
| 가상 메모 | `t02_vault_notes`, `t03_personal_notes` | Supabase | 포함 |
| 복구 사본·감사 | `t10_note_backups`, `t10_restore_audit` | Supabase | 포함 |
| 기기·회수·접근 기록 | `t11_devices`, `t12_revoked_identities`, `t12_access_events` | Supabase | 포함 |
| 탐지 보조 표 | `xdr_brute_force_blocklist`, `xdr_brute_force_failures` | Supabase | 선택 |
| 조치 접수 기록 | 운영자가 설정한 경로의 SQLite 파일 | 운영자 호스트 설정 | 7-4 참고 |
| 비밀값 | `.env`, 키, 토큰, 기기 개인키 | 로컬·서버 보관소 | **백업 대상 아님**: Git·백업 파일·문서에 넣지 않고 담당자가 재발급 |

### 7-2. 백업 절차 (Supabase)

1. 백업 전 앱 사용을 멈춥니다(쓰기가 없는 상태에서 일관된 사본을 받기 위함).
2. 선택 A: Supabase 대시보드의 Database → Backups에서 제공되는 백업을 확인합니다(제공 여부는 요금제에 따르며 **미확인**).
3. 선택 B: 표 단위 내보내기. 연결 문자열은 Supabase 대시보드에서 받아 환경변수 `DATABASE_URL`에만 넣고 파일·Git·답변에 적지 않습니다.

```powershell
pg_dump --data-only --no-owner --table=public.t02_vault_notes --table=public.t03_personal_notes --table=public.t10_note_backups --table=public.t10_restore_audit --table=public.t11_devices --table=public.t12_revoked_identities --table=public.t12_access_events --file=..\백업\keshev-data-날짜.sql $env:DATABASE_URL
```

4. 백업 파일은 **저장소 밖**의 폴더에 둡니다. `t03_personal_notes`·`t10_note_backups`에는 메모 본문이 있으므로 Git에 커밋하지 않고 접근을 제한합니다.
5. 파일 이름에 날짜를 넣고, 마지막 백업 시각을 저장소 밖의 개인 기록에 남깁니다.

### 7-3. 복원 절차 (Supabase)

1. 새 Supabase 프로젝트(또는 비운 프로젝트)에 `README.md`의 순서대로 스키마 SQL을 실행합니다: `supabase/notes_seed.local.sql`, `supabase/personal_notes.local.sql`, `supabase/personal_notes_rls.local.sql`, `supabase/t03_revoke_direct.local.sql`, `docs/sql/t10_note_backups.sql`, `docs/sql/t10_restore_audit.sql`, `docs/sql/t11_devices.sql`, `docs/sql/t12_ops.sql`.
2. 시드 SQL이 이미 넣은 행과 백업의 행이 겹칠 수 있으므로, 복원 전에 해당 표가 비어 있는지 확인합니다.
3. 백업 파일을 `psql $env:DATABASE_URL -f <백업 파일>`로 적용합니다.
4. 복원 뒤 확인: 각 표의 행 수가 백업 시점과 같은지, **`t12_revoked_identities`(회수된 신원)가 반드시 복원되었는지**를 먼저 봅니다. 회수 기록이 빠진 채 앱을 열면 회수된 신원이 다시 열릴 수 있으므로, 확인 전에는 앱을 열지 않습니다.
5. 메모 한 건 단위 복구(`GET/POST /api/note-restore/:id`)는 `t10_note_backups`의 사본을 읽으므로, 이 표를 먼저 복원해야 동작합니다.

### 7-4. 조치 접수 SQLite

- 파일 경로는 운영자 호스트 설정(`databasePath`)이 정하며, 이미 존재하는 SQLite 파일이어야 합니다(`on-client/src/actions/action-startup-config.mjs`는 자동 생성·이전을 하지 않음). 학생이 경로를 정하거나 바꾸지 않습니다.
- 이번 환경에서는 조치 설정이 없어 이 파일을 사용하지 않았고, 실제 경로·내용은 **미확인**입니다.
- 설정이 있는 환경에서의 절차: 앱을 종료한 뒤 그 파일을 저장소 밖에 복사해 백업하고, 복원은 앱을 종료한 상태에서 같은 경로의 파일을 백업본으로 교체합니다. 헤더가 SQLite 형식이 아니거나 링크이면 설정 검사가 거부합니다.
- 제한: 접수 기록을 복원해도 이미 연동 시스템에 전달된 조치의 효과는 되돌려지지 않으므로, 결과는 재조회로만 확인합니다.

### 7-5. 제한

- 백업 시점 이후의 변경은 복원되지 않습니다. 자동 백업 일정은 만들지 않았습니다.
- 위 명령과 Supabase 백업 기능은 이번에 실행하지 않았으므로 동작 여부는 **미확인**입니다.
- 서버가 이 계획을 실행하거나 검증하지 않습니다.

- 접근 제어 유지: 다른 `Host` 403, `Sec-Fetch-Site: cross-site` 403, 쿼리 문자열 400, `POST /api/pc-status` 404, 다른 `Origin`의 POST 403. 브라우저에 `student/pc-status.mjs`는 제공되지 않음(404)
- 기존 API: `/api/diagnostics`·`/api/vulnerabilities` 200, `/api/me`·`/api/events`는 SDP 미연결이라 503(원래 동작)
- 이 PC의 실측 결과: CPU·메모리·디스크는 `ok`. 네트워크·방화벽·Windows 기록은 **`policy_blocked`(확인 불가)**. 실행 정책 5개 범위가 모두 `Undefined`이고 `-File` 실행에서 `UnauthorizedAccess`가 나는 것을 확인함
- 정책 우회 없이는 막히므로, 스크립트 **로직**만 하니스 세션(프로세스 범위 정책이 이미 `Bypass`인 읽기 전용 `Get-*`)에서 따로 실행해 보았습니다. 일반 권한에서 어댑터 수, 방화벽 3프로필 켜짐 여부, System·Application 경고·오류 건수가 나왔고 출력에 IP·SSID·로그 원문은 없었습니다(0.8~3.5초). 이것은 **앱 경로의 검증이 아닙니다.**

### 9-3. 모의 데이터로 확인한 것 (실제 설정이나 권한을 바꾸지 않음)

- 조회 모듈 12개 시험: 값·단위·시각, CPU 구간 0이면 확인 불가, 디스크 접근 거부, 메모리 이상값, 항목별 부분 실패, 알 수 없는 사유 코드 차단, 잘못된 형식 거부, 여분 필드(IP·SSID 등) 제거, 예외 흡수, 중복 실행 공유, 비Windows 처리, 스크립트에 쓰기·실행 명령 없음

### 9-4. 확인하지 못했거나 코드만 검토한 것

- 실제 브라우저 화면(레이아웃, 포커스 링, 스크린리더 읽기), 키보드 조작은 직접 확인하지 못했습니다. 아래 절차로 사용자가 확인해야 합니다.
- 실행 정책이 스크립트를 허용하는 PC에서의 앱 경로 결과(네트워크·방화벽·Windows 기록), 8초 시간 초과(`timeout`)와 8KB 출력 제한(`output_too_large`)이 실제 프로세스에서 작동하는지는 코드 검토만 했습니다. 자식 프로세스 환경변수 허용 목록도 코드 검토만 했습니다.
- Node 24.19.0, 설치형 앱, `start-alekov.ps1` 경로, SDP 연결 상태(`connected`)에서의 표시, 관리자 권한이 필요한 경우의 `access_denied` 표시는 실제로 확인하지 않았습니다.
- 0.2.21 업데이트와 「내 PC 상태」·`appearance.json`의 제공 방식은 프로젝트에서 근거를 찾지 못했습니다(미확인).
- 「핵심 3가지가 먼저 보이게」는 학생 카드 안에서만 지켰습니다. 카드의 화면 위치(보호 현황의 다섯 번째 카드)는 제공 `index.html`이 정하며 바꾸지 않았습니다. 색·여백은 `style.css`가 제공 파일이고 CSP(`style-src 'self'`)가 인라인 스타일을 막아 기존 클래스만 썼습니다.

### 9-5. 사용자가 직접 확인할 절차

1. `README.md`의 「마무리」 실행 명령으로 서버를 켜고 `http://127.0.0.1:5189/`를 연다.
2. 「보호 현황」을 아래로 내려 「학생 상태·알림 표시」 카드의 「내 PC 상태」를 본다. 자동으로 한 번 조회된다.
3. CPU·메모리·디스크가 작업 관리자와 대략 맞는지, 측정 시각·단위가 보이는지 본다.
4. 네트워크·방화벽·Windows 기록이 「확인 불가 / PowerShell 실행 정책…」으로 표시되는지 본다(이 PC의 현재 설정 기준).
5. Tab 키만으로 「다시 조회」→「기록 삭제」→「삭제 확인」/「취소」를 누르고, 포커스 표시가 보이는지, 조회 중 연타해도 한 번만 조회되는지 본다.
6. 두 번 이상 조회한 뒤 「직전 조회와 비교」의 이전 조회값·시각·증감 설명을 확인한다. 「기록 삭제」 뒤에는 「비교할 기록 부족」이 나와야 한다.
7. 「SDP 연결 상태」 줄이 「SDP 미연결」로 PC 조회 상태와 따로 보이는지 확인한다.

### 9-6. 디자인 추가 기록 (사이드바 대시보드, 글라스 카드, 라이트·다크)

- **구현 범위:** `student/extension.mjs` 한 파일. 사이드바(개요 / PC 상태 / 변화 비교 / PC 점검)와 테마(시스템·라이트·다크)는 「학생 상태·알림 표시」 카드 **안쪽** 패널이며 앱 전체 내비게이션이 아닙니다. 제공 파일(`index.html`, `style.css`, `app.js`, `server.mjs`)은 이번 디자인에서 추가로 고치지 않았습니다. `appearance.json`은 만들지 않았습니다.
- **스타일 방식:** 앱 CSP(`style-src 'self'`)가 `<style>`·`style=` 속성을 막으므로 `CSSStyleSheet` + `adoptedStyleSheets`(CSSOM)로 넣었고, 모든 규칙은 `.kpc` 안쪽에만 걸립니다. 실제 Edge에서 CSP 위반 없이 적용됨을 확인했습니다. 지원하지 않는 브라우저는 스타일 없이 읽을 수 있는 문서 모양이 됩니다.
- **테마:** 처음에는 `prefers-color-scheme`을 따르고, 직접 고르면 `localStorage`의 `kesheb.pcTheme.v1`(`light`/`dark`만)에 저장합니다. 「시스템」을 누르면 저장을 지웁니다. 앱의 나머지 화면은 다크 모드가 없어(제공 `style.css`) 패널만 다크가 되고 주변 카드는 라이트로 남습니다.
- **글라스:** 반투명(약 78~80%) 카드 + `backdrop-filter`. `backdrop-filter`가 없거나 `prefers-reduced-transparency: reduce`이면 불투명 배경이고, `forced-colors`에서는 테두리를 씁니다. 글자·수치·버튼은 불투명입니다.
- **상태 구분:** 정상(✓)·주의(▲)·확인 불가(?)·참고(i)를 아이콘과 글자로 함께 표시합니다. 정상/주의는 CPU·메모리 90%, 디스크 남은 비율 10% 기준의 참고 기준이며 보안 판정이 아닙니다.
- **대비(WCAG 2.x, 소스의 색 토큰을 읽어 계산):** 본문·보조 글자 4.5:1 이상, 배지·버튼 글자 4.5:1 이상, 포커스 링·UI 경계·강조선 3:1 이상. 반투명 카드는 배경 그라데이션 양 끝과 장식 블롭을 얹은 색 중 최악 조합에서 계산했습니다. 라이트의 보조 설명이 패널 바깥 배경 최악 조합에서 4.80:1로 여유가 가장 작습니다. 실제 화면의 픽셀을 측정한 값은 아닙니다.
- **이 PC에서 실제 확인한 것(Edge 헤드리스, 임시 프로필, 개발자 도구 프로토콜):** 라이트·다크 × 넓은 화면(1440px) 4개 메뉴, 키보드 Tab 포커스 링(라이트·다크), 패널 폭 400px에서 사이드바→상단 메뉴 전환과 가로 넘침 없음(4개 메뉴), 불투명 대체 배경(`backdrop-filter`를 CSS로 끈 모의), 콘솔 예외 없음. 로그의 503·404는 SDP 미연결 상태의 기존 API와 정적 파일 요청입니다.
- **미검증:** (1) 좁은 화면은 실제 좁은 창이 아니라 패널 폭을 400px로 줄여 컨테이너 쿼리를 확인한 것입니다. 앱 전체가 `body{min-width:1024px}`라 실제 좁은 창은 가로 스크롤이 생기며 제공 파일이라 바꾸지 않았습니다. (2) Chrome·Firefox·Safari, 스크린리더 낭독, 고대비 모드, `prefers-reduced-transparency`가 실제로 켜진 환경, `backdrop-filter` 미지원 브라우저 실물. (3) 시스템 테마를 앱이 열려 있는 동안 바꿀 때의 자동 반영(코드는 있으나 실물 확인 안 함), 사용자가 직접 마우스·키보드로 눌러 본 조작. (4) 설치형 앱에서의 모양은 검증하지 않았습니다. (5) 카드의 화면 위치(보호 현황의 다섯 번째)는 제공 `index.html`이 정합니다. (6) `#student-status`가 `aria-live="polite"`라 조회가 끝나 다시 그릴 때 스크린리더가 패널 내용을 길게 읽을 수 있으나 확인하지 않았습니다.
